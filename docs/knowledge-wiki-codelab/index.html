This codelab walks through my repo: Anthropic's knowledge-wiki quickstart (from anthropics/claude-quickstarts, MIT license, see LICENSE), run end to end on the core tier, plus a small web app in demo/ that asks the built wiki questions.

The idea, simply: instead of rereading a whole filing cabinet for every question, an agent reads it once and writes a well-sourced binder. Later questions are answered from the binder.

The assignment's input is the images from the in-class hackathon: 12 photos of AI companies' career-fair brochures. I first ran the quickstart on its own worked example (a real take-private deal's SEC filings) to learn it, then built a second wiki from the brochure photos with the same notebook and agents. The demo app asks the brochure wiki.

What the repo does:

  • Turns the brochure photos into text, and fetches the worked example's SEC filings (Squarespace) from EDGAR.
  • Has Claude Managed Agents read them once into a wiki: plain markdown pages in a memory store, where every fact carries its source and the date it was true, and conflicts between documents stay conflicts.
  • Checks the build against the platform's own records, not just the agents' reports.
  • Answers questions from the wiki read-only, and compares the cost with searching the raw documents.
  • Serves a one-page FastAPI app for asking the wiki.

Every number here comes from the saved outputs of a notebook on main; the notebook section is named for each.

What it costs

Build (once). The notebook uploads the 25 batches and starts one Managed Agents session. A lead agent runs one dynamic workflow in four phases, each starting only after every agent of the previous phase has finished:

  1. Extract: one wiki-extractor per batch files what the documents say into the wiki.
  2. Resolve: one wiki-resolver works through the wiki's open questions.
  3. Analyze: one wiki-analyzer per batch re-reads it against the wiki and adds what was missed.
  4. Organize: one wiki-organizer tidies the whole wiki and its index.

Ask (many times). Each question opens a fresh session with the wiki mounted read-only, and the analyst agent may only read, glob and grep, so asking can never change the wiki.

You need Python 3.11 or later, an Anthropic API key with Managed Agents access, and API credit: the build is a paid run.

git clone https://github.com/prekshapraveen2502/knowledge-wiki.git
cd knowledge-wiki
python3.11 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

Create .env in the repo folder (it is in .gitignore):

ANTHROPIC_API_KEY=sk-ant-...
COOKBOOK_BUDGET_USD=30
COOKBOOK_RECORDS_DIR=/full/path/to/a/folder/outside/the/repo
  • COOKBOOK_BUDGET_USD caps the build. It must be at least the estimate the notebook prints and should be below your credit balance, so the budget, not your credit, is what stops a run that goes over.
  • COOKBOOK_RECORDS_DIR must be a full path (~ is not expanded). Without it, records go to a temporary folder that may be cleared on restart.

Fetch the filings (free; the script reads the SEC contact from the shell, not .env):

export EDGAR_USER_AGENT="Your Name your-email@example.com"
python fetch_data_room.py --tier=core

Open the notebook with the .venv kernel and run cells one at a time, not Run All, which would run straight into the paid cells.

From the schema cell on, the notebook creates things on your Anthropic account and lists them in created.json in the records folder. Don't restart the kernel until the build has finished: a restart starts a new records folder and a second set of everything. Run the consolidation-prompts cell only once: each run creates the agents again.

Run the cell under The consolidation prompts. It prints the estimate and the budget check, then creates the five agents. My run printed an estimate of $25.77 against a $30 budget.

Run Describe the goal (free: it only prints the message), then Run the build. Keep the machine awake and don't touch the kernel. My run ended:

After 30.5 minutes: the agent finished, with no run left open.

The lead agent's report is what to check: batches_extracted and batches_analyzed equal to 25, organized: true and failures: []. My other counts (10 resolved, 294 still open, 219 index entries) will differ from run to run.

If the build errors, don't rerun the cell: that starts a second paid build.

An agent's report is only its own claim, so the next cells check the platform's records.

Run the export cell (it saves each question session's transcript to the records folder), then the clean-up cell. By default it keeps the wiki store and removes everything else:

Kept the wiki store: memstore_.... To delete it later: client.beta.memory_stores.delete('memstore_...')

Copy that store id for the app. Afterwards, created.json in the records folder lists only the wiki store.

The kit's normalize_any turns PDFs, Word, Excel, PowerPoint and email into text, but raises on images. So brochures/convert_brochures.py adds the missing piece: for each photo in brochures/images/ it turns the photo upright (phones store rotation in EXIF), shrinks it to at most 2000 px, wraps it in a one-page PDF and sends it through the kit's own normalize_pdf, which reads the rendered page, figures included. It writes brochures/docs/IMG_xxxx.txt (not in Git) with a provenance line:

[SOURCE: in-class hackathon brochure | file: IMG_4595.JPG | photographed: 2026-10-30 | note: transcribed from a photo]

python brochures/convert_brochures.py

Then build with a copy of the notebook, brochures_knowledge_wiki.ipynb, pointed at those files:

COOKBOOK_DOCS=brochures/docs
COOKBOOK_BUDGET_USD=10

COOKBOOK_DOCS is the notebook's own switch for your own documents: it skips the worked example's extra files. Two lines in the copy's schema cell were changed so the extractors aren't told they're reading a Squarespace deal: the extractor's opening sentence and the store's description. The rest of the prompts is unchanged.

Run the cells as before, up to and including the build checks, then skip to the clean-up cell: the notebook's question cells and its comparison ask about the Squarespace deal. My brochure run filed 12 of 12 documents with no failures, all checks on the platform's records passed, and the file check found only 2 dangling links, both in the wiki format's own SKILL.md.

The worked example's wiki is kept too: switching the app back is a matter of changing WIKI_STORE_ID and recreating the app's analyst, with no rebuild.

demo/app.py is a FastAPI app with one page that asks the brochure wiki: type a question, or pick one of four examples (one company in detail, a comparison across companies, a fact across all brochures, and something the brochures don't say), and get the answer with numbered sources, and the reads, tokens, cost and time below it. Each question gets a fresh read-only session, which the app archives as soon as the answer is in (interrupting it first if it is still running). The answer goes into the page as text, never as HTML, because it comes from documents an agent read.

pip install -r demo/requirements.txt
python demo/setup_demo.py

setup_demo.py creates the app's own analyst agent and environment (no model runs) and prints two lines for .env. It refuses to run again once they are there, so it can't make duplicates.

WIKI_STORE_ID=memstore_...        # the brochure wiki, printed by the clean-up cell
DEMO_ENVIRONMENT_ID=env_...
DEMO_AGENT_ID=agent_...

uvicorn demo.app:app --host 127.0.0.1 --port 8000

Open http://127.0.0.1:8000. When you're done, python demo/teardown_demo.py archives the app's agent and environment and keeps the wiki.

  • The brochure wiki cost $0.32 to build from 12 photos and filed every one of them; adding images took one small converter and two changed prompt lines; the rest of the kit ran as shipped.
  • On the worked example, one build of $18.86 gave a wiki that answered the notebook's questions at a mean of $0.004 each, against $0.058 for searching the raw documents.
  • Checking the platform's records, not the agents' reports, is what showed each build complete: every input read, phases in order, no failures.
  • The worked example's wiki is not perfect: 6 name mismatches, 1 dangling link, and an answer that broke an "entities only" instruction.

What went wrong for me, so you can avoid it:

  • My first two builds ran out of credit partway (billing_error) and left nothing usable. Have more credit than the budget, and keep the budget below the balance.
  • A kernel restart mid-run created a second set of agents, environment and store. Each attempt's created.json lists what it made, which is what I used to clean up before trying again.
  • The notebook's ask doesn't close a session if you interrupt it, so the app closes its sessions in a finally block.
